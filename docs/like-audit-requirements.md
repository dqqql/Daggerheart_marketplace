# 宝库点赞日志记录需求

日期：2026-09-18  
状态：已实现；上线与远端 migration 仍由管理员按部署流程确认。

## 一、目标与边界

记录必要的点赞行为数据，供出现刷票疑虑时导出并离线排查。当前只做记录，不开发在线分析、异常评分、告警或管理页展示。

- 不要求账号登录或验证码，不增加正常点赞步骤。
- **不修改现有资源 JSON、导出字段、数据结构及 RAG 同步接口。**
- 日志与资源数据独立存储，不通过公开接口返回。
- 不修改现有点赞、取消点赞及推荐加权规则，不清理历史赞数。
- 从功能上线后开始记录，不补造历史数据。
- 记录用于识别可疑行为，不将 IP、浏览器编号直接等同于自然人，也不自动处罚作者或读者。

## 二、必须记录的数据

| 字段 | 内容与要求 |
| --- | --- |
| `eventId` | 每次操作的唯一编号，供导出时去重。 |
| `occurredAt` | 服务端生成的 UTC 时间，精确到毫秒，使用 ISO 8601 格式。 |
| `entryId` | 被操作资源的稳定 ID，不以标题作为关联依据。 |
| `action` | 点赞或取消点赞。若请求在判断当前状态前失败，可记为 `unknown`，不要猜测动作。 |
| `outcome` | 成功、未改变状态或失败；失败只记简短原因码，不记录完整请求或异常堆栈中的私密信息。 |
| `reasonCode` | 失败或未改变状态的简短、枚举式原因码；不保存请求体、完整异常或私密上下文。 |
| `countDelta` | 此次实际计票变化：`+1`、`-1` 或 `0`，不含推荐值加权。执行结果确实无法确认时使用 `null`，不可把未知写成零。 |
| `visitorId` | 本站随机生成的匿名浏览器编号，不是账号或硬件指纹。 |
| `visitorFirstSeenAt` | 该编号由服务器首次签发的时间，不代表此人首次访问网站。 |
| `visitorIdStatus` | 本次请求已携带有效编号、新签发编号或编号不可用。服务器无法仅凭首次请求判断 Cookie 是否被禁用。 |
| `ipHash` | 可信客户端 IP 的稳定哈希；尽量沿用现有点赞身份算法，不存原始 IP。地址不可用时记为空，不编造公共身份。 |
| `identityVersion` | 身份计算规则的版本号，用于区分日后可能变化的哈希、地址来源或编号规则，不包含实际盐值或密钥。 |

`countDelta` 应依据实际执行结果记录，不能从前端点击、界面显示值或推荐加权值推算。取消点赞后应保留原点赞及本次取消的两条历史日志。

## 三、辅助信息

只记录粗粒度信息，作为组合判断的辅助线索：

| 字段 | 建议取值 |
| --- | --- |
| `browserFamily` | Chrome、Edge、Safari、Firefox、其他或未知。 |
| `osFamily` | Windows、Android、iOS、macOS、Linux、其他或未知。 |
| `deviceClass` | 手机、平板、桌面或未知。 |

不必保存完整 User-Agent。这些特征可能相同或识别不准确，不能单独用于认定同一用户。

## 四、匿名浏览器编号

- 使用本站第一方 Cookie 保存随机编号，设置 `Secure`、`HttpOnly` 和适当的 `SameSite`。
- 编号及首次签发时间由服务器生成，并能验证来源；不要直接信任客户端自填的编号或签发时间。
- 同一浏览器保留 Cookie、切换网络后，编号保持不变。
- 清除 Cookie、换浏览器或使用无痕模式后可能产生新编号，这是已知局限，不尝试使用其他特征偷偷恢复旧编号。
- 无法保存 Cookie 时仍允许正常点赞，不直接判为异常。
- 编号及签发时间仅说明浏览器凭条的延续性，不能证明使用者身份。
- 不把个性化 Cookie 写入可公开缓存的资源响应，避免不同访客收到相同编号；建议通过非缓存的点赞相关接口签发。

## 五、不采集的数据

不采集真实姓名、联系方式、账号信息、原始 IP、完整 Cookie、完整浏览历史、硬件指纹、鼠标轨迹或按键记录。

第一版不记录页面停留时间或外链点击。用户可能此前已在其他地方读过资源，这些信号对判断刷票帮助有限。

## 六、存储、访问与可靠性

- 日志使用现有 D1 数据库 `the-great-vault` 的独立表 `like_audit_events`，不另建日志服务。
- 不把日志写进现有资源 JSON，不混入资源导出结果，不放进公开静态网站目录。
- 不提供公开日志查询接口，不增加管理员页面。
- 只允许授权管理员读取和导出，不向前台返回其他访客的任何身份信息。
- 日志写入失败，不得把已经成功的点赞显示成失败，或引导用户重复操作；服务端应留下不含身份明细的错误记录，便于发现漏记。
- 失败记录使用 Pages Functions 的结构化 `console.error`；本仓库不配置 Worker observability。管理员可用 `npx wrangler pages deployment tail --project-name the-great-vault --status error` 实时排查，但平台日志可用性与保留期不保证审计事件完整性。
- 记录失败和数据库执行结果不确定时如实标注，不声称日志完整无缺。
- 操作明细与匿名浏览器 Cookie 均固定保留 **90 天**；维护工具按 UTC cutoff 清理到期明细。
- Worker 经 `waitUntil` 尽力写入审计事件，日志可能因后台写入失败或中断而存在缺口，不声称完整无缺。
- 补充简短的数据用途及保留期说明，不增加验证码或强制确认步骤。

## 七、离线导出

- 支持授权管理员按日期范围导出 JSONL，通过维护工具完成，无需网页入口；导出包含 `events.jsonl`、脱敏的 `entries.json` 与覆盖信息 `manifest.json`。
- 导出包含上述字段，并提供资源 ID、标题、作者的对照表；不要附带投稿邮箱、密钥等无关字段。
- 同时注明导出时间、日志覆盖时间及已知缺失情况。
- 资源改名或下架后，已有日志仍应保留稳定的资源 ID，不因资源删除自动级联清除审计日志；历史标题能否保留由现有资源历史能力决定。
- 日志不会直接判定谁刷票，也不自动扣票。是否需要分析及如何处理，由后续人工决定。

## 八、验收清单

- 点赞、取消点赞均留下独立记录，取消不抹去此前日志。
- 有效计票变化与实际操作一致，不将推荐值调整记录成新增点赞。
- 同一浏览器换网络后，浏览器编号不变，IP 哈希可以变化。
- 无 Cookie 时仍可点赞，日志准确标注本次编号状态。
- 时间和首次签发信息由服务器生成，无法从客户端任意伪造有效的历史签发信息。
- 个性化编号不进入公共缓存，不同访客不会因缓存共享同一个编号。
- 普通访客不能读取日志或获得其他访客的身份信息。
- 日志写入异常不影响已成功的点赞响应，服务端能够发现记录失败。
- 现有资源 JSON 的字段与结构完全不变，RAG 同步正常。

## 九、已确定的实现决策

1. 使用 D1 表 `like_audit_events`，不使用独立私有文件存储。
2. 明细与 Cookie 均为固定 90 天；以 JSONL 作为定期维护导出格式。
3. 匿名凭据使用身份版本字段区分签发与验证规则，当前不在公开接口暴露其内容。

本需求不要求上线新的分析系统、账号体系、验证码、限流或浏览器指纹功能；部署和 migration 执行状态不由本文档宣称完成。
