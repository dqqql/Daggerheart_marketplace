# 点赞防刷方案（仅讨论，不实施）

## 建议结论

先做可信 IP 去重加短时限流，不要求注册登录，不改历史票数。前台已按确认后的要求显示“点赞数 + 推荐值 × 10”，后台仍单独保存真实点赞记录；防刷检测应看真实点赞变化，而非加权显示值。观察异常后再考虑人机验证，而不是让所有正常读者先过一道验证。

## 当前代码事实

- `frontend/_worker.js` 的 `toggleLike` 已按条目与 IP 哈希查询、插入或撤销点赞。
- `migrations/0001_initial.sql` 已有 `(entry_id, ip_hash)` 联合主键。同一身份反复点赞并不会一直增加票数。
- `getClientIpHash` 当前优先采用 `X-Forwarded-For` 首项，其次才是 `CF-Connecting-IP`，缺失时退回共同的 `local-dev` 身份。
- 尚不能据此确认历史票数存在多少异常，更不能归因到某个作者；本次未对线上接口进行攻击式验证。

Cloudflare 文档说明：请求已带有 `X-Forwarded-For` 时，Cloudflare 会追加代理地址，而不是替换所有原值。因此，结合当前实现判断，首项不应直接成为可信投票身份。参见 [Cloudflare HTTP headers](https://developers.cloudflare.com/fundamentals/reference/http-headers/)。

## 第一阶段：修正身份与并发处理

1. 在 Cloudflare 生产入口使用其提供的可信访客地址，不接受用户自填的转发链首项；生产环境缺少可信地址时拒绝点赞，开发环境的替代身份必须显式隔离。
2. 保持“同一 IP 对同一条目最多一个有效赞”，保留撤销能力。并发重复请求应得到可解释结果，不能出现数据库冲突导致的 500；具体幂等实现先单独设计，不擅自改 API。
3. 浏览器增加一个短暂点击锁，仅用于防误触；真正的限制必须在服务端，不能依赖前端按钮。
4. 不自动清除历史票数。改变 IP 解析后，部分旧身份可能无法对应；先评估实际数据再决定过渡方式，不能承诺零影响。

代价：同一宿舍、家庭或公司共用公网 IP 时可能共用一票；切换网络仍可能得到新身份。匿名 IP 去重只能增加重复刷票成本，不能证明“一人一票”。

## 第二阶段：限频与观察

- 初始候选阈值：单 IP 每分钟最多 20 次点赞或撤销请求，超过后提示稍后再试；这是待验证的起点，不是已批准参数。
- 采用平台支持的共享限流设施，不用单个 Worker 的内存计数冒充跨实例限制；配置能力、费用和套餐限制在实施前核实。
- Cloudflare Workers 的 Rate Limiting binding 按数据中心计数且为最终一致，不是全球严格统一计数；适合削弱突发请求，不应作为“一人一票”的唯一保证。参见 [Rate Limiting](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/)。
- 记录短时异常频次和条目增长变化，使用哈希身份及有限保留期，不向前台暴露 IP 或身份明细。
- 高增长只能触发观察，不直接等同刷票；转发、活动和推荐都可能带来真实集中访问。
- 第一阶段可不改数据库结构；第二阶段若需要审计表或新绑定，先提交具体方案并取得授权。

## 暂不建议

- 强制登录、注册后等待一天：降低本已不高的点赞参与率，也挡不住多账号。
- 每次点赞都做人机验证：正常读者负担过大；仅在确实发生自动化滥用后评估。
- 把所有 IPv6 地址简单按网段合并：可能误伤共享网络，需有实际流量证据。
- 因疑似刷票处罚作者或随意扣票：不能据匿名请求证明作者本人组织了刷票。

## 验收标准（未来实施时）

- 修改自带转发头不能在同一可信 IP 下制造新票。
- 同一身份同一条目最多一个赞，刷新一致，撤销有效，并发不产生 500。
- 正常低频点赞不受打扰；高频请求得到明确的限流提示，并可在冷却后恢复。
- 不要求登录，不改变推荐值含义，不自动处理历史票数。
